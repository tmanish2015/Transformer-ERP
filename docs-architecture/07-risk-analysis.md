# Risk Analysis

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| 1 | **Multi-tenant RLS mistakes leak data across companies** — this is the single biggest architectural deviation from the proven Tradeflow reference (which never had to solve this). A missed `company_id` predicate on any one of ~60+ tables is a real cross-tenant data leak. | Medium | Critical | Generate RLS policies programmatically (same `do $$ loop` mechanism, extended) rather than hand-writing per table; add an automated test/lint step that asserts every table with a `company_id` column has exactly 4 policies referencing `current_company_id()`; run Supabase advisor (`get_advisors`) after every schema migration. |
| 2 | **Scope explosion** — 16 modules + AI + workflow engine + 4 portals is an enormous surface. Spec explicitly warns against generating everything at once, but pressure to "show progress across everything" risks shallow, half-wired modules everywhere instead of deep, working verticals. | High | High | Hard-enforce the phased roadmap: one full vertical (Workshop) proven end-to-end before starting the next (Rental). Resist requests to "also add a bit of Y" mid-phase. |
| 3 | **Generalized Workflow Engine is speculative complexity** — spec asks for a configurable approval matrix, but Tradeflow's own production reference only ever needed one hardcoded approval column (and even that shipped as a bug-fixed afterthought). Building a generic engine before a second real use case exists violates simplicity-first and risks an over-abstracted, under-used subsystem. | Medium | Medium | Deferred by design (see Roadmap Phase 6, conditional). Ship hardcoded per-document approval columns first; generalize only once 2+ modules independently need multi-step approval. |
| 4 | **Auto-posting trigger correctness for new document types** (repair jobs, rental invoices) — Tradeflow's GL auto-posting trigger hardcodes account codes per document type; getting the debit/credit mapping wrong for a new type (e.g. rental security deposit — is it a liability or income?) silently corrupts the trial balance. | Medium | High | Have the mapping table reviewed by an actual accountant/domain expert before writing the trigger, not just inferred from the spec. Add a "GL entries balance to zero" invariant check as a Postgres constraint/test, not just application-level trust. |
| 5 | **Serial-number / asset-lifecycle state machine bugs** — rental_assets and repair_jobs both have long, branching status lifecycles (10+ states). An invalid transition (e.g. invoicing a rental asset that's still "running") is a real operational/financial bug, not cosmetic. | Medium | High | Enforce legal transitions in a Postgres `check` constraint or trigger (reject invalid `old.status → new.status` pairs) rather than trusting the frontend to only offer valid buttons. |
| 6 | **AI Assistant capabilities (fault diagnosis, spare recommendation) can produce plausible-sounding but wrong technical guidance** in a domain (high-voltage electrical equipment) where a bad suggestion has real safety/financial consequences. | Medium | High | Frame every AI output as a *recommendation the engineer must verify*, never an autonomous action (no auto-ordering spares, no auto-approving estimates from AI output alone). Log every AI suggestion + human decision for audit. |
| 7 | **Desktop (Electron) + multi-tenant SaaS combination is unusual** — Tradeflow's Electron build assumes one Supabase project per install (`preload.js` injects a single config). A multi-tenant SaaS desktop client instead needs company/session selection at runtime, which the reference pattern doesn't cover. | Medium | Medium | Treat this as new engineering, not reuse — desktop client authenticates against the shared multi-tenant Supabase project like the web build does; `preload.js`'s config-injection role shrinks to just environment/API-URL, not per-customer project identity. |
| 8 | **Testing Lab needs to work as a fully standalone module** for pure-play lab customers (per spec's target-user list), but it's designed with optional FKs into workshop/rental/manufacturing. Risk of accidentally hard-coupling it during implementation for convenience. | Low | Medium | Explicit test case in Sprint 9: issue a certificate with zero repair/rental/production context, no shortcuts. |
| 9 | **Vendor/customer/technician portals as route-trees-within-one-app** (not separate apps) risk RBAC/nav leakage — a technician seeing an admin-only route because a guard was forgotten on one new page. | Medium | Medium | Every new page added to any portal route tree must carry an explicit `<RequirePermission>` — treat this as a checklist item in code review, not assumed from route nesting alone. |
| 10 | **Reference project (Tradeflow) keeps evolving during this build** — patterns copied today may drift from Tradeflow's own future fixes (e.g. its licensing bug-fix migrations). | Low | Low | Treat Tradeflow as a frozen reference snapshot for architecture purposes; don't chase its future changes unless a specific pattern proves broken in practice. |
